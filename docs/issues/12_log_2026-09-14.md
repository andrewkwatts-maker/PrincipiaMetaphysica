### Arithma under the formulas, and the first switch-combination search

**The shared third track.** Arithma coverage was 51 of 121 simulation modules,
and the reason was cost: each conversion meant hand-writing the stub guard,
expression construction, an evaluation environment and a comparison. Fifty-three
modules had already copied that guard, and the copies are what let a *degraded*
arithma become a hard CI failure.

`simulations/core/arithma_formula.py` is that scaffolding once. A simulation
declares name, LaTeX hint, a build lambda, its registry `inputs`, mathematical
`constants`, and the plain-Python statement — and gets `latex()`, `compact()`,
`evaluate()`, `derivative()` and `check()`.

`check()` is the point: it compares the Arithma tree against the Python callable
on registry values, so three independent statements of one formula get verified
against each other rather than merely coexisting. **Two tests prove it can
fail** — a deliberately drifted Python reference must be caught — because a
checker that always agrees verifies nothing.

No magic numbers anywhere in the path. `inputs` maps symbols to REGISTRY PATHS
fetched at evaluate time; mathematical constants come from **Arithma's own
constant table** (`initialize_defaults` / `lookup_value`), because pi is not a
physics parameter and does not belong in the parameter registry, but must not be
a literal either. `provenance()` reports each number's origin, and a missing
input **refuses to evaluate** rather than guessing.

First batch: the four b_3 relations — w_0, n_gen, the racetrack exponent, the
Freudenthal quartic. All four agree with their Python statements at **rel = 0.0**,
all export LaTeX, all roundtrip through the compact form. Coverage ratchet
installed at the measured 51/121, with a companion test that fails if the
baseline goes stale.

### The switch-combination search, and what it found about the preferred path

`simulations/core/switch_search.py` enumerates combinations of the open forks and
reports what each does. It obeys the anti-tuning rule literally: every
combination reported, rows ordered by **digest** (any ordering derived from the
outcomes is the first step towards ranking by fit), verdict always
`NO_SELECTION_MADE`.

What it can legitimately decide is **internal consistency**, which references no
measurement. Five checks, all measurement-free:

| check | what it asks |
|---|---|
| `phi_is_a_g2_form` | is dim ann(phi) = 14, as g2 requires by definition? |
| `n_gen_is_integral` | is b_3/8 an integer? A generation count is a number of things |
| `re_t_is_the_solved_vacuum` | is the live Re(T) the declared potential's stationary point, or a calibration? |
| `arithma_track_agrees` | do the three statements of each formula agree? |
| `joyce_branch_is_decidable` | can a branch claiming the Joyce route actually compute it? |

**First result, over `g2_form_convention` x `re_t_adoption` x `b3_origin`, 16
combinations: 3 internally consistent, 13 not.**

And the finding that matters: **the PREFERRED path is among the inconsistent
ones**, carrying two CONTRADICTIONS —

    phi_is_a_g2_form            dim ann(phi) = 6, g2 requires 14
    re_t_is_the_solved_vacuum   live Re(T) = 7.086, the only minimum is 37.853

Both were already on the books individually. This is the first time the framework
has been able to **report that its own adopted configuration contains them**, as
a computed verdict rather than two separate register entries a reader has to
connect.

Neither contradiction is resolved here, because both resolutions are author
rulings: adopting `g2_form_convention = octonion_derived` (cost measured at zero
— no physics test fails, no published parameter moves) and
`re_t_adoption = computed_vacuum` (cost measured and real — the eta_b match is
destroyed).

**What closure would look like, now recognisable.** Exactly one internally
consistent combination whose free set has no `LOAD_BEARING_INPUT` left. Both
numbers are reported per row, so that state can be identified the moment it
arrives. The module does not declare it, and will not.

## 2026-09-14 (eighteenth pass) — the third track has never run, and CI had been red for thirty commits

The brief for this pass was "put Arithma underneath every formula": convert the
70 uncovered simulation modules, run `.check()` on each, and record every
disagreement. **Not done, and it should not be done.** Three measurements say
why, and the pass turned into the thing the brief's own verification gate was
supposed to prevent.

### THE BLOCKER: no published arithma can build an expression

`pyproject.toml` pins `arithma>=2.0.1,<2.0.3` in the `[sims]` extra. Both
versions in that range ship:

    Expression = None   # "Wave 3 -- not yet exposed via PyO3"
    Integer    = None
    Variable   = None

The compiled Rust extension **does** load — `is_rust_backend()` returns True —
and exports exactly two names, `is_rust_backend` and `version_rust`. There is no
expression object at any published version.

Consequences, each measured rather than inferred:

* `ArithmaFormula.check()` returns `BACKEND_UNAVAILABLE` with `agrees: None`.
  Converting 70 modules would have produced 70 more checks that cannot
  disagree. **The conversion was declined on that ground.** A drift check with
  one of its two statements missing is not a weak check; it is not a check.
* `tests/test_arithma_formula_track.py` carried a MODULE-LEVEL
  `skipif(not available())`. All 13 tests skipped, the coverage ratchet among
  them. The ratchet pinning third-track coverage had never once executed.
* `AutoGenerated/arithma_trees.json` is written by a build step that reports
  `OK` and contains **zero formulas** with `arithma_available: false`.

A working arithma demonstrably exists on the author's machine — the tracked
`AutoGenerated/dependency_chains.json` carries `arithma_available: true` with
169+ formulas holding real trees. It has never been published. **This is an
author ruling, not something this pass can decide: either a working arithma is
released, or the third track's status changes on the books.** Everything the
triple-track guard claims to verify is, outside that one machine, verified by
two tracks.

### THE COVERAGE NUMBER WAS COUNTING A WORD

"Coverage is 51 of 121 simulation modules" — the figure the ratchet pinned and
the brief instructed be raised — counts files in which the **substring**
`arithma` appears. Measured over those 51:

    modules declaring an ArithmaFormula ........................ 0
    modules carrying the legacy copied `try: import arithma` guard ... 51

Zero. All 51 are the scaffolding `ArithmaFormula` exists to replace. The metric
could be raised by writing the word in a docstring, and raising it was the
brief's stated per-batch deliverable.

Worse: `b3_candidate_sweep` — the only module in the repository that declares an
`ArithmaFormula` at all — contains no `SimulationBase` and is therefore invisible
to the corpus the metric scans. The worked example of the third track sat outside
the thing measuring third-track coverage.

Both counts now ratchet separately, declarations are counted by **parsing for
`ArithmaFormula(...)`** so prose cannot move the number, and a test requires the
two counts to DIFFER — a split that made no difference would be a loosening in
disguise. Declarations: **1**. Mentions: **51**. The gap is the backlog.

### CI HAD BEEN RED FOR THIRTY CONSECUTIVE COMMITS

The brief's verification gate reads "currently 1953 passed, 0 failed … Do not
commit a red suite." Measured: **CI failed on every push from run 152
(2026-09-06) through run 181 (2026-09-13)** — thirty runs, seven tests, over
eight days. Every commit in that window was pushed onto a red suite, and each
commit message recorded a locally-green count that CI did not reproduce.

The seven failures reproduce exactly in a clean container, to the assertion
value. Three unrelated causes:

**(a) A plotting extra was deleting four formulas from every CI build.**
`test_arithma_b3_coverage_never_regresses` asserted `565 >= 569`. The four
missing formulas were not lost — four **simulations** never ran. Three modules
under `PM/consciousness` imported matplotlib (the `[plots]` extra, which CI does
not install) at module scope; `run_all_simulations` swallowed the ImportError:

    four_dice_sampling        four-dice-branch-count
    gnosis_unlocking          gnosis-coherence-enhancement
                              gnosis-unlocking-probability
    orch_or_pair_shielding    pair-shielding-enhancement

This is the **third** appearance of one defect shape: nine simulations that had
never run behind an `except ImportError`; a stub arithma that imported and could
not compute; now a figure library gating physics. With matplotlib imported where
it is used, CI produces 569 again and SSOT compliance goes from 819/819 over 91
simulations to **846/846 over 94**.

**(b) The ratchet was comparing two different builds.**
`PrincipiaMetaphysica/AutoGenerated/dependency_chains.json` is **tracked** and was
regenerated on the author's machine with a working arithma: 569 formulas, 45
degraded, `arithma_available: true`. All five baselines sit **exactly** on that
file's values, which is where they were transcribed from.
`metaphysica/AutoGenerated/` is gitignored and rebuilt by CI with the stub, where
21 formulas whose only tree is an arithma tree degrade — giving 66. The test's
`_load()` prefers the metaphysica tree. So CI compared a stub-backend build
against a working-backend baseline and could never pass.

The two backend-dependent ceilings are now measured separately and selected by
the artifact's own `arithma_available` flag. `total_formulas` is asserted
**identical** under both, because arithma decides whether a formula carries a
tree, not whether it exists — letting those drift apart is what hid the missing
simulation behind the missing package for eight days.

The docstring claim that "degradation is caused by MISSING EXPRESSIONS, not a
missing package" is true with a backend and **false without one**; it now says so.

**(c) Three tests asked whether arithma imports, not whether it works.**
They guarded with `pytest.importorskip("arithma")` and then called
`Expression.number` — the exact distinction `arithma_backend.py` was written to
make, unused. `racetrack_vacuum.superpotential_expression` did the same with
`except ImportError` and died on `NoneType.variable`. All now go through the
probe; the dynamic-range requirements are unchanged and skip rather than fail.

**A correction to the record.** The commit that last left these failing
attributed it to arithma 2.0.2 being unable to "represent the span the physics
uses (1.9e-93 to 4.8e34)". That diagnosis is wrong. The span is not the problem;
there is no arithma object to hold a number in.

**Result: CI run 182 is GREEN** — 1936 passed, 0 failed, first success in 30 runs.

### THE SWITCH SEARCH REPORTED A CONTRADICTION THE FRAMEWORK DOES NOT HAVE

`switch_search` scored `BACKEND_UNAVAILABLE` as a **CONTRADICTION**. An absent
backend leaves no second statement to disagree with, so all 16 combinations
reported a contradiction that is about the environment rather than the theory,
and `n_internally_consistent` read 0 everywhere except the author's machine.

It is `VACUOUS` by the module's own definition — a check that cannot fail in
this configuration — and still counts against its row, because an unevaluated
check is not a passed one. What is reported separately is whether a row is
blocked **only** by checks this environment could not evaluate:

    combinations searched ....................................... 16
    internally consistent ........................................ 0
    blocked ONLY by checks unevaluable here ...................... 3

Those three reproduce the author's result exactly, and the structure is the
finding:

| fork | value in all three |
|---|---|
| `g2_form_convention` | `octonion_derived` |
| `re_t_adoption` | `computed_vacuum` |
| `b3_origin` | **free** — `input_24`, `arc_flag_stabiliser`, `d4_root_shell` |

`joyce_twisted_sector` is excluded, and **not** for an environment reason: its
`joyce_branch_is_decidable` check is genuinely VACUOUS — the branch asserts what
it cannot compute. The distinction between "vacuous in the theory" and
"unevaluable in this environment" is now carried per check (`evaluable_here`),
with a test requiring that the theory vacuity is never laundered as an
environment artifact.

The two live CONTRADICTIONS on the **preferred path** are unchanged and
unresolved, both author rulings:

    phi_is_a_g2_form            dim ann(phi) = 6, g2 requires 14
    re_t_is_the_solved_vacuum   live Re(T) = 7.086, the only minimum is 37.853

`switch_search` also shipped with **no tests at all**. Its central promises —
reports every combination, never returns "the best one", never orders by
agreement with an experimental anchor — were assertions in a docstring.
`tests/test_switch_search.py` now enforces them, including a source scan
rejecting any mention of DESI / NuFIT / Planck / PDG / CODATA / sigma / residual
inside `consistency_checks`, and a test requiring digest ordering to be
distinguishable from problem-count ordering (otherwise the ordering promise
cannot be tested at all).

### ADDENDUM — the neutrino mass sum is published three ways, all DERIVED

Looking for remaining hard-coded choices to port to switches (the pass's Task B),
the search for `calibrated` / `we use` / `chosen` turned up something better than
a fork. **The framework publishes four values for Σm_ν**, three of them `DERIVED`:

| row | value (eV) | status | source |
|---|---|---|---|
| `neutrino.mass_sum` | 0.101214 | FITTED | `neutrino_mixing_v17_2` |
| `neutrino.sum_masses` | 0.101975 | DERIVED | `matter_sector_complete_v19` |
| `particle.sigma_m_base_eV` | 0.060517 | DERIVED | `neutrino_sector` v26.0 |
| `particle.sigma_m_refined_eV` | 0.042517 | DERIVED | `neutrino_sector` v26.0 |

A spread of **2.4×** between derived statements of one physical quantity. No
measurement is involved in noticing this: it is the theory disagreeing with
itself, which is exactly what `switch_search`'s CONTRADICTION category is for,
and it is now check number five there.

**The stated explanation does not hold.** `neutrino_sector`'s module docstring
says:

> NOTE: companion module (neutrino_mixing.py) publishes a different Σm_ν
> under the opposite mass ordering — the two scenarios are alternatives,
> not simultaneous predictions.

`neutrino_mixing` is **not** under the opposite ordering. It predicts INVERTED
(`neutrino.ordering = INVERTED`, PREDICTED, from that module), and
`neutrino-mass-hierarchy-v19` states INVERTED as the framework's ordering. So the
ordering is not what separates 0.102 from 0.043, and the note explains a
discrepancy on grounds that are not the case.

What *is* the case, from the formula register: `neutrino-sum-prediction-v18`
computes "Sum of neutrino masses **in normal hierarchy** … sum ~ 0.06 eV", and
0.0605 is what `neutrino_sector` registers as `sigma_m_base_eV` while its own
docstring says it computes the *inverted* sum. **A normal-hierarchy number is
being carried under an inverted-hierarchy label, inside a framework that
predicts inverted.** That is the most likely root, and it is stated here as the
lead to check, not as a finding — resolving it is a physics ruling and belongs
to the author.

`neutrino.mass_sum` is deliberately EXCLUDED from the check: it is FITTED, and a
fit disagreeing with a derivation is not the theory contradicting itself.
`base` and `refined` are both included on purpose — the module presents refined
as superseding base, yet registers both as DERIVED, so the register carries two
live derived answers rather than one.
